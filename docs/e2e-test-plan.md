# End-to-end acceptance scenarios

Use a **fresh demo database**, not the original PC database. Follow [Windows laptop setup](windows-laptop-setup.md), sign in with the development administrator you created locally, and keep test credentials out of Git. The demo seed provides Espresso, Cappuccino, ingredients, cups, a vendor, customers, tables, a warehouse, riders, recipes, and sample lots. It does not seed financial transactions or extra user passwords.

Create distinct test users and roles in Identity. The administrator can assign the exact permissions shown on the Roles page. Sign out and sign in after permission changes so the JWT contains the new grants. Use separate users for cashier, kitchen staff, storekeeper, purchasing staff, and approvers; do not give a cashier blanket admin access merely to get through a test.

Record the order, KOT, lot, requisition, return, and payment numbers generated by the app. For every rejected operation, expect a validation message or Problem Details response, not a browser error banner or silent success. Refresh each page after a successful write to confirm persistence.

## A. Access and master data

1. Sign in as the development administrator. Check Overview, Identity profile, and all implemented workspaces. Change your own password, sign out, confirm the old password fails and the new password works. Test required fields, weak passwords, duplicate email, disabled-user login, and a read-only role trying a write URL/API.
2. In Identity, create the test roles/users and assign only the permissions needed for each duty. Verify that menus, action buttons, and API endpoints enforce the same permissions. Test permission revocation followed by sign-out/sign-in.
3. In Administration, inspect company/branch/alert settings, approval routes, and audit history. Set a test approval tier or expiry threshold, reload, and confirm it persists; restore the intended value afterward. Verify a user without `administration.settings.manage` cannot save it.
4. In Catalog, create one active item group, unit, menu item, raw material, vendor, customer, dining table, warehouse, rider, and recipe. Confirm dropdowns show names and relevant active records, not GUID entry fields. Test duplicate codes, invalid email, and international phone format (`+` followed by 8–15 digits). Deactivate a reference and confirm new Inventory selections reject it. Check inspection requirement and criterion configuration.

## B. Inventory, sale, and kitchen

5. As a storekeeper, receive eligible ingredients into a named warehouse and lot with manufacturing/expiry dates. Confirm on-hand and available increase and the ledger shows a receipt. Attempt a duplicate lot, expired receipt/issue, negative receipt, and quantity exceeding available; each must be rejected appropriately.
6. Reserve stock, confirm on-hand stays unchanged while reserved increases and available falls. Release it and verify the inverse. Issue stock and verify on-hand/available and the immutable movement history. Try to issue more than available, blocked or expired stock, and a stale/concurrent update.
7. As cashier, create dine-in, takeaway, and delivery orders using Catalog selections. For dine-in select a free table, add Espresso/Cappuccino, and confirm. Attempt a second active order on the same table. Test required/invalid customer phone and unavailable/disabled items.
8. As kitchen staff, select the confirmed order in Kitchen and generate the first KOT. Verify required recipe ingredients are reserved, queue/history update, special instructions persist, and a second open browser receives the SignalR update. Add another item to the Sales order and generate an additional KOT for only the new item. Progress preparation statuses and verify history.
9. Cancel a pre-issue KOT and verify reservations release. After goods issue, test that cancellation does **not** silently return physical stock; the appropriate reversal/wastage path is required. Test duplicate KOT generation and inadequate stock.
10. As cashier, request a discount; as a separate manager approve it. Attempt billing before approval (rejected), then bill and close. Verify gross amount, discount, total and status history. Repeat a no-discount order. Test validation for a percentage above 100 and a stale approval request.

## C. Production and purchasing

11. As planner, create a plan from an active menu item/recipe, release the production order, review material requirement/reservation, post goods issue, record actual consumption and wastage, and complete it. Compare theoretical vs actual variance and stock ledger. Attempt release without sufficient eligible ingredients and completion before required issue.
12. As requester, create a purchase requisition for a Catalog material/vendor. As the configured department manager, approve it. As buyer, create an RFQ, capture quotations, compare/select a vendor, and create a PO. Test a missing quotation and an unauthorized approval.
13. Exercise each seeded PO approval value band: PKR 25,000; PKR 25,001–100,000; above PKR 100,000. Use distinct Purchasing Manager, Finance Manager, and Owner/Admin approvers as configured; verify the PO cannot advance before all required approvals.
14. Receive material against the approved PO. For an inspection-required item, capture each criterion, inspector, date, remarks and supporting reference. Verify failed material does not enter unrestricted stock; a passed receipt creates the correct lot/ledger entry. Test vendor return without deleting the receipt.

## D. Payment, return, and void

15. For a billed order, create a Cash, COD, or Bank Transfer payment. Verify and settle it with the appropriate role. Test a duplicate/overpayment and a user lacking `payments.verify`. Create a separate billed order using Easypaisa and JazzCash **simulators**; verify their success/failure paths without real credentials or network payments.
16. Find the paid original bill in Returns, create an RMA against its line, and inspect it. Try an unsealed, damaged, expired, unverified-batch or failed-inspection item: it must not add stock. For an eligible sealed item, record all evidence and obtain the Store/QC approval before restocking. Verify Inventory movement and Returns status history.
17. Approve a credit note/refund request, then process it in Payments. For a uniquely matched settled wallet payment, confirm simulator routing and remaining refundable balance; test an amount above the unrefunded balance and repeated processing. Where no original payment can be matched, confirm the UI explicitly describes a manual/simulated fallback.
18. Request a void before payment and then after payment on separate orders. Verify the configured Sales Manager and Finance approval steps, original Sales status, credit/refund linkage, and audit trail. A void must never physically delete the order or its payment history.

## E. Expiry, permissions, and resilience

19. Check expiry alerts at the configured 15/7/3-day thresholds with test lots. Confirm expired/blocked lots cannot be reserved or issued. Restore any temporary alert setting after this test.
20. Repeat a representative create/approve/issue/refund request using a read-only role, an unrelated module role, a disabled user, and an expired/revoked JWT. Expect 403 or 401 as appropriate, with no database mutation.
21. At desktop and mobile viewport widths, navigate every implemented page, open/close forms, submit invalid data, use search/filter/dropdowns, and reload after writes. Watch for the Blazor error banner and browser console/network failures. Run `dotnet restore BrewNest.sln`, `dotnet build BrewNest.sln --no-restore`, and `dotnet test BrewNest.sln --no-build` again after UI testing.

## Scope boundary

Delivery assignment, Finance posting/profit, and Reporting dashboards are planned modules rather than finished workflows. Catalog riders are master data only. This checklist is an acceptance guide; executing it on one machine does not prove every browser, concurrency interleaving, or external payment/provider scenario. Record actual results and defects for each step before sign-off.
